    <h1 class="page-headline">Gaming industry still in the scope of attackers in Asia</h1>    <p class="sub-title">Asian game developers again targeted in supply-chain attacks distributing malware in legitimately signed software</p>

    <div class="article-authors d-flex flex-wrap">  <div class="article-author d-flex">  <a href="/blog/en/our-experts/marc-etienne-m-leveille/" title="Marc-Etienne M.Léveillé">   <picture>  <source srcset="https://web-assets.esetstatic.com/tn/-x45/blog/2013/06/Marc-Etienne-M.Leveille.png" media="(max-width: 768px)" />   <img class="author-image me-3"  src="https://web-assets.esetstatic.com/tn/-x45/blog/2013/06/Marc-Etienne-M.Leveille.png" alt="Marc-Etienne M.Léveillé"  /></picture>  </a>  <div class="author-text"><p><a href="/blog/en/our-experts/marc-etienne-m-leveille/" title="Marc-Etienne M.Léveillé"><b>Marc-Etienne M.Léveillé</b></a></p></div></div> </div>

    <p class="article-info mb-5">

        <span class="d-none d-lg-inline">&nbsp;&bull;&nbsp;</span>

    </p>


    <div class="hero-image-container">
         <picture>  <source srcset="https://web-assets.esetstatic.com/tn/-x266/blog/2019/03/Gaming_Asia.jpg" media="(max-width: 768px)" />   <source srcset="https://web-assets.esetstatic.com/tn/-x425/blog/2019/03/Gaming_Asia.jpg" media="(max-width: 1120px)" />  <img class="hero-image"  src="https://web-assets.esetstatic.com/tn/-x700/blog/2019/03/Gaming_Asia.jpg" alt="Gaming industry still in the scope of attackers in Asia"  /></picture>    </div>
</div>

                    <div class="article-body">
    <p>This is not the first time the gaming industry has been targeted by attackers who compromise game developers, insert backdoors into a game’s build environment, and then have their malware distributed as legitimate software. In April 2013, Kaspersky Lab <a href="https://media.kasperskycontenthub.comhttps://web-assets.esetstatic.com/blog/sites/43/2018/03/20134508/winnti-more-than-just-a-game-130410.pdf" target="_blank" rel="noopener">reported</a> that a popular game was altered to include a backdoor in 2011. That attack was attributed to perpetrators Kaspersky called the Winnti Group.</p>
<p>Yet again, new supply-chain attacks recently caught the attention of ESET Researchers. This time, two games and one gaming platform application were compromised to include a backdoor. Given that these attacks were mostly targeted against Asia and the gaming industry, it shouldn’t be surprising they are the work of the group described in Kaspersky’s “Winnti – More than just a game”.</p>
<h2>Three Cases, Same Backdoor</h2>
<p>Although the malware uses different configurations in each case, the three affected software products included the same backdoor code and were launched using the same mechanism. While two of the compromised products no longer include the backdoor, one of the affected developers is still distributing the trojanized version: ironically, the game is named Infestation, and is produced by Thai developer Electronics Extreme. We have tried informing them several times, through various channels, since early February, but without apparent success.</p>
<p>Let’s look at how the malicious payload is embedded and then look into the details of the backdoor itself.</p>
<h2>Embedding the payload</h2>
<p>The payload code is started very early during the execution of the backdoored executable file. Right after the PE entry point, the standard call to the C Runtime initialization (<span style="font-family: courier new, courier, monospace;">__scrt_common_main_seh</span> in Figure 1) is hooked to launch the malicious payload before everything else (Figure 2). This may suggest that the malefactor changed a build configuration rather than the source code itself.</p>
<p><div class="caption center"><a href="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-01-at-2.16.17-PM.png"><img class="size-full wp-image-122828" src="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-01-at-2.16.17-PM.png" alt="" width="1574" height="286" /></a><p class="caption-text">Figure 1 Clean executable file entry point</p></div></p>
<p><div class="caption center"><a href="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-01-at-2.15.40-PM.png"><img class="size-full wp-image-122829" src="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-01-at-2.15.40-PM.png" alt="" width="1976" height="614" /></a><p class="caption-text">Figure 2 Compromised executable file entry point</p></div></p>
<p>The code added to the executable decrypts and launches the backdoor in-memory before resuming normal execution of the C Runtime initialization code and all the subsequent code of the host application. The embedded payload data has a specific structure, seen in Figure 3, that is parsed by the added unpacking code.</p>
<p><div class="caption center"><a href="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-18-at-2.08.21-PM.png"><img class="size-full wp-image-122830" src="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-18-at-2.08.21-PM.png" alt="" width="1440" height="410" /></a><p class="caption-text">Figure 3 Embedded payload structure</p></div></p>
<p>It includes an RC4 key (which is XORed with 0x37) that is used to decrypt a filename and the embedded DLL file.</p>
<h2>The malicious payload</h2>
<p>The actual malicious payload is quite small and only contains about 17 KB of code and data.</p>
<h2>Configuration</h2>
<p>Illustrated in Figure 4, the configuration data is simply a whitespace-separated list of strings.</p>
<p><div class="caption center"><a href="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-25-at-11.39.28-AM.png"><img class="size-full wp-image-122831" src="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-25-at-11.39.28-AM.png" alt="" width="1328" height="184" /></a><p class="caption-text">Figure 4 Payload configuration data</p></div></p>
<p>The configuration consists of four fields:</p>
<ol>
<li>C&amp;C server URL.</li>
<li>Variable (<em>t</em>) used to determine the time to sleep in milliseconds before continuing the execution. Wait time is chosen randomly in the range 2/3 <em>t</em> to 5/3 <em>t</em>.</li>
<li>A string identifying a campaign.</li>
<li>A semicolon-separated list of executable filenames. If any of them are running, the backdoor stops its execution.</li>
</ol>

<h2>Reconnaissance report</h2>
<p>A bot identifier is generated from the machine’s MAC address. The backdoor reports information about the machine such as the user name, computer name, Windows version and system language to the C&amp;C server and awaits commands.  The data is XOR encrypted with the key “<span style="font-family: courier new, courier, monospace;">*&amp;b0i0rong2Y7un1</span>” and base64-encoded. The data received from the C&amp;C server is encrypted using the same key.</p>
<h2>Commands</h2>
<p>This simple backdoor has only four commands that can be used by the attacker:</p>
<ul>
<li><span style="font-family: courier new, courier, monospace;">DownUrlFile</span></li>
<li><span style="font-family: courier new, courier, monospace;">DownRunUrlFile</span></li>
<li><span style="font-family: courier new, courier, monospace;">RunUrlBinInMem</span></li>
<li><span style="font-family: courier new, courier, monospace;">UnInstall</span></li>
</ul>
<p>The commands are pretty much self-explanatory. They allow the attacker to run additional executables from a given URL.</p>
<p>The last one is perhaps less obvious. The UnInstall command doesn’t remove the malware from the system. After all, it is embedded inside a legitimate executable that still needs to run. Rather than removing anything, it disables the malicious code by setting the following registry value to 1:</p>
<ul>
<li><span style="font-family: courier new, courier, monospace;">HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\ImageFlag</span></li>
</ul>
<p>When the payload is started, the registry value is queried and execution is aborted if set. Perhaps the attackers are trying to reduce the load from their C&amp;C servers by avoiding callbacks from uninteresting victims.</p>
<h2>Second stage</h2>
<p>Based on ESET telemetry, one of the second stage payload delivered to victims is <span style="font-family: courier new, courier, monospace;">Win64/Winnti.BN.</span> As far as we can tell, its dropper was downloaded over HTTPS from <span style="font-family: courier new, courier, monospace;">api.goallbandungtravel[.]com</span>. We have seen it installed as a Windows service and as a DLL in <span style="font-family: courier new, courier, monospace;">C:\Windows\System32</span> using the following file names:</p>
<ul>
<li>cscsrv.dll</li>
<li>dwmsvc.dll</li>
<li>iassrv.dll</li>
<li>mprsvc.dll</li>
<li>nlasrv.dll</li>
<li>powfsvc.dll</li>
<li>racsvc.dll</li>
<li>slcsvc.dll</li>
<li>snmpsvc.dll</li>
<li>sspisvc.dll</li>
</ul>
<p>The samples we have analyzed were actually quite large, each of them about 60 MB. This is, however, only for appearance because the real size or the PE file is between 63 KB and 72 KB, depending on the version. The malware files simply have lots of clean files appended to them. This is probably done by the component that drops and installs this malicious service.</p>
<p>Once the service runs, it appends the extension <span style="font-family: courier new, courier, monospace;">.mui</span> to its DLL path, reads that file and decrypts it using RC5. The decrypted MUI file contains position-independent code at offset 0. The RC5 key is derived from the hard drive serial number and the string “<span style="font-family: courier new, courier, monospace;">f@Ukd!rCto R$.</span>” — we were not able to obtain any MUI files nor the code that installs them in the first place. Thus, we do not know the exact purpose of this malicious service.</p>
<p>Recent versions of the malware include an “auto-update” mechanism, using C&amp;C server <span style="font-family: courier new, courier, monospace;">http://checkin.travelsanignacio[.]com</span>. That C&amp;C server served the latest version of the MUI files encrypted with a static RC5 key. The C&amp;C server was not responding during our analysis.</p>
<h1>Targets</h1>
<p>Let’s start with who is <em>not</em> targeted. Early in the payload, the malware checks to see if the system language is Russian or Chinese (Figure 5). In either case, the malware stops running. There is no way around this: the attackers are simply not interested in computers configured with those languages.</p>
<p><div class="caption center"><a href="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-14-at-10.01.18-AM.png"><img class="size-full wp-image-122832" src="https://web-assets.esetstatic.com/blog/2019/03/Screen-Shot-2019-02-14-at-10.01.18-AM.png" alt="" width="1722" height="558" /></a><p class="caption-text">Figure 5 Language checks before running the payload</p></div></p>
<h2>Distribution statistics</h2>
<p>ESET telemetry shows victims are mostly located in Asia, with Thailand having the largest part of the pie. Given the popularity of the compromised application that is still being distributed by its developer, it wouldn’t be surprising if the number of victims is in the tens or hundreds of thousands.</p>
<p><a href="https://web-assets.esetstatic.com/blog/2019/03/Chart.jpg"><img class="aligncenter size-full wp-image-122834" src="https://web-assets.esetstatic.com/blog/2019/03/Chart.jpg" alt="" width="878" height="545" /></a></p>
<h1>Conclusion</h1>
<p>Supply-chain attacks are hard to detect from the consumer perspective. It is impossible to start analyzing every piece of software we run, especially with all the regular updates we are encouraged or required to install. So, we put our trust in software vendors that the files they distribute don’t include malware. Perhaps that’s the reason multiple groups target software developers: compromising the vendor results in a botnet as popular as the software that is hacked. However, there is a downside of using such a technique: once the scheme is uncovered, the attacker loses control and computers can be cleaned through regular updates.</p>
<p>We do not know the motives of the attackers at this point. Is it simply financial gain? Are there any reasons why the three affected products are from Asian developers and for the Asian market? Do these  attackers use a botnet as part of a larger espionage operation?</p>
<p>ESET products detect this threat as Win32/HackedApp.Winnti.A, Win32/HackedApp.Winnti.B, the payload as Win32/Winnti.AG, and the second stage as Win64/Winnti.BN.</p>
